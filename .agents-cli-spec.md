# Agent Spec

## Overview

Extend the existing Ameria Bank tariff-monitoring modular monolith with robust bilingual
intent and offering resolution, native Google ADK human-in-the-loop (HITL), and explicit
safe-failure behavior. The supported catalog remains two product families and thirteen
configured offerings: four consumer-loan offerings and nine mortgage offerings.

The system uses a coarse-grained ADK workflow around the existing deterministic
`TariffPipeline`. Acquisition, normalization, source discovery, PDF handling, semantic
extraction, validation, persistence, change detection, scheduling, and publication remain
deterministic application services. The ADK workflow owns meaningful control boundaries:
request/scope resolution, pipeline invocation, outcome routing, native human-input pause
and resume, and final user-facing reporting.

Upgrade and lock `google-adk` from the installed 2.9.0 to the latest approved stable
version, 2.9.2, before adopting workflow resumability. Preserve the configured Gemini
model identifiers unless the user explicitly requests a model change.

## Example Use Cases

1. A new English or Armenian chat session briefly introduces consumer loans and
   mortgages, names a few representative offerings, and offers the complete catalog.
2. A user asks for an offering using an alias, synonym, transliteration, typo, or
   imprecise name. Deterministic matching resolves it when confidence is sufficient;
   otherwise Gemini classifies only among catalog IDs. A still-ambiguous result produces
   a conversational clarification instead of a guess.
3. A user asks for current tariffs. The system returns the latest accepted snapshot with
   its as-of time. If it is older than seven days, the system labels it stale and asks
   whether to refresh. If no accepted snapshot exists, it offers a monitoring run.
4. A user explicitly requests monitoring. The agent starts the durable run, says it is
   monitoring, and waits for up to two minutes. If still running, it returns the run ID
   and safe status without claiming fresh data.
5. A typed client calls `POST /api/v1/runs` with canonical product/offering IDs. No
   natural-language agent or Gemini classification is required, but the worker executes
   the same durable ADK monitoring workflow and deterministic pipeline.
6. A nominal or effective interest rate changes by at least three percentage points. The
   candidate and its documents are quarantined, the ADK workflow emits `RequestInput`,
   and the run becomes `AWAITING_REVIEW` until a reviewer resumes the invocation.
7. A current official PDF and webpage disagree for the same field and conditions. The
   reviewer selects a captured candidate, rejects both, or supplies a value plus reason
   and reference to existing captured evidence. The resumed workflow revalidates the
   decision before publication.
8. A user asks what changed. The system reports accepted changes from the last sixty
   days. If the last change is older, it says no change was detected in the last sixty
   days and may identify the older last-change date.

## Architecture

Use a modular monolith with one conversational ADK surface and a coarse-grained,
durable ADK monitoring workflow:

- ADK chat resolves natural-language intent and catalog scope, handles clarification,
  invokes narrow application tools, and presents evidence-bound results.
- FastAPI retains typed non-chat run, status, question, and read-only operational review
  interfaces.
- The scheduler submits typed family commands; it is not an agent or graph node.
- The worker claims queued runs and starts/resumes the durable ADK monitoring workflow.
- The workflow invokes the same concrete `TariffPipeline` used by all monitoring entry
  paths; internal monitoring stages are not decomposed into graph nodes solely for
  appearance.
- PostgreSQL business tables are authoritative for runs, candidates, evidence, reviews,
  snapshots, changes, and publication state.
- PostgreSQL-backed ADK session/event persistence is authoritative for workflow
  invocation state, including paused interrupts, resume inputs, and completion events.
- Business and workflow state are correlated by `run_id`, `review_id`, `session_id`,
  `invocation_id`, and `interrupt_id`.
- pgvector and PostgreSQL full-text search continue to provide hybrid retrieval.

### Workflow Nodes

Use nodes only at meaningful control and resume boundaries:

1. `resolve_scope` for a typed run command or previously resolved chat command.
2. `execute_monitoring` to call the deterministic `TariffPipeline`.
3. `route_outcome` to branch on accepted, failed, or review-required outcomes.
4. `request_human_input` to emit native ADK `RequestInput` with a typed review contract.
5. `apply_review_decision` to call deterministic revalidation and publication logic.
6. `build_final_result` to emit bounded user-facing workflow output.

### Considered Alternatives

- Keep only the imperative pipeline and custom review endpoints: rejected because it
  would not demonstrate native ADK pause/resume HITL.
- Convert every acquisition/extraction/persistence stage into a graph node: rejected
  because those boundaries contain no human or agent decision, pass large rich
  artifacts, and already have tested retry and transaction semantics.
- Let Gemini orchestrate downloads, validation, authority, or publication: rejected
  because it weakens security, auditability, and the non-fabrication guarantee.

## Intent and Product Resolution

The explicit intent taxonomy is:

- `LIST_SUPPORTED_PRODUCTS`
- `ANSWER_INDEXED_TARIFF_QUESTION`
- `GET_CURRENT_TARIFFS`
- `START_MONITORING_RUN`
- `GET_RUN_STATUS`
- `GET_CHANGE_HISTORY`
- `UNSUPPORTED_OR_GENERAL`
- `CLARIFICATION_RESPONSE`

Resolution proceeds in this order:

1. Unicode-aware normalization, case folding, punctuation/spacing normalization, and
   reviewed transliteration normalization.
2. Exact canonical ID, localized name, alias, and synonym matching.
3. Conservative deterministic fuzzy matching with configurable score and top-candidate
   gap thresholds.
4. Constrained Gemini classification using only enumerated intent, family, and offering
   candidates from the catalog.
5. Conversational clarification when confidence remains insufficient or candidates are
   too close.

The versioned seed catalog owns English and Armenian display names, aliases, synonyms,
and optional transliterations. Gemini may select only known catalog IDs and cannot create
new products or offerings.

Family-level behavior is intent-sensitive:

- family-wide monitoring runs every configured offering in that family;
- broad overview questions summarize all indexed offerings in the family;
- a question expecting one tariff value asks the user to choose an offering.

The agent responds in Armenian for Armenian requests and English for English requests.
For mixed language it follows the dominant language and defaults to English when unclear.

## Session and First-Interaction Behavior

Conversational session state stores only:

- whether the short product introduction has been shown;
- pending intent and clarification candidates;
- the latest resolved family and offering.

It does not create cross-session personal memory. Monitoring and review workflow sessions
are separately durable because they are execution state rather than user-profile memory.

The first assistant response in each chat session briefly names the two configured product
families, gives a few representative offerings, and offers the full list. It describes
them as configured/supported offerings and does not claim that each has an accepted
snapshot.

## Entry Points and Tools

### Entry Points

- ADK chat: resolves free-form user language and submits canonical commands.
- `POST /api/v1/runs`: submits a canonical family/offering monitoring command without
  requiring conversational agent use.
- Run/status and question/history HTTP APIs: provide typed machine access.
- Scheduler: submits independent consumer-loan and mortgage family runs.
- Worker: claims runs and executes the durable ADK monitoring workflow.
- ADK Web: sole decision interface for native reviewer HITL in the assignment prototype.

### Agent-Facing Tools

- `list_supported_products`: return the versioned localized catalog.
- `resolve_request`: return typed intent/family/offering candidates and ambiguity state.
- `answer_tariff_question`: answer from accepted active indexed evidence only.
- `get_current_tariffs`: retrieve latest accepted snapshots and freshness metadata.
- `start_tariff_monitoring`: submit a typed run and return durable identifiers.
- `wait_for_monitoring_run`: poll bounded stored status for at most two minutes.
- `get_monitoring_run`: retrieve persisted run and offering outcomes.
- `get_change_history`: retrieve accepted snapshot changes under bounded filters.
- `list_pending_reviews`: expose review cases to the reviewer workflow.
- `apply_review_decision`: validate and transactionally apply a resumed ADK human input.

No tool exposes arbitrary network, filesystem, shell, database, repository, or SQL access.

## Current Tariffs and History

- “Current” means the latest accepted snapshot, never an unaccepted extraction or newest
  source document.
- The freshness threshold is configurable and defaults to seven days.
- A stale snapshot may be shown only with its as-of time and a prominent warning; the
  agent asks before refreshing unless the user explicitly requested a refresh.
- Missing accepted data produces no tariff answer and offers a monitoring run.
- “What changed?” defaults to the latest accepted comparison within sixty days.
- “Show history” defaults to the last thirty days.
- Explicit bounded date ranges and limits are honored.
- History queries never trigger acquisition or monitoring automatically.
- A missing previous snapshot is a first observation, not a failure or change.

## Native ADK Human-in-the-Loop

The reviewer is the human participant in ADK HITL. Review decisions are supplied through
native ADK `RequestInput` and resume behavior in ADK Web. A custom FastAPI decision route
must not impersonate a human response or mutate publication state.

### Complete HITL Scenarios

1. Large rate change: an otherwise valid nominal or effective interest-rate change of at
   least three absolute percentage points requires approval before becoming current.
2. Conflicting official sources: a current official PDF and current official webpage
   provide incompatible values for the same field and conditions.
3. Unresolved source applicability: captured official documents cannot be confidently
   assigned to the offering or effective period.
4. Missing required field with usable evidence: bounded extraction repair cannot resolve
   a required field, but the captured sources are usable for human inspection.

Multiple official sources that agree do not require review; retain all relevant evidence.
Low-confidence routing is based on deterministic ambiguity, evidence, validation, and
repair signals, not a model-generated confidence percentage.

### Reviewer Decisions

For a source conflict, the reviewer may:

- choose an evidence-backed candidate;
- reject all candidates; or
- propose a value with a reason and a reference to existing captured evidence.

Every decision is revalidated against schema, offering scope, conditions, and evidence.
An unsupported third value cannot be accepted. Approval atomically activates the accepted
snapshot, eligible changes, and quarantined RAG documents. Rejection preserves the prior
accepted snapshot. Duplicate decisions are idempotent.

Review-pending documents and candidates remain hidden from ordinary RAG. A newer candidate
or accepted observation for the same offering and issue scope marks older pending reviews
`SUPERSEDED`; a superseded interrupt cannot publish even if a stale resume is attempted.

### Run Status

Use:

- `QUEUED`
- `RUNNING`
- `AWAITING_REVIEW` (nonterminal while the ADK invocation is paused)
- `SUCCEEDED`
- `PARTIAL_SUCCESS`
- `FAILED`

After all required decisions, all-approved runs succeed; mixed accepted and rejected/failed
offering outcomes are partial success; runs with no accepted offering fail. Extraction may
internally report `completed_with_review`, but the enclosing monitoring run remains
`AWAITING_REVIEW` while resumable input is pending.

## Safe Failure Behavior

- Website timeout/unavailability: retry only transient errors with bounded backoff; then
  fail the offering and preserve the last accepted state.
- HTTP 404/missing PDF: do not retry as transient; record a precise manifest reason. A
  failed optional linked document may coexist with usable official sources, but it cannot
  support a value.
- Invalid MIME, PDF signature, excessive size, unsafe redirect, or disallowed host: fail
  that source closed with no model invocation.
- Parsing failure or unusable/low-quality PDF/OCR result: fail the offering without HITL;
  preserve the previous accepted snapshot.
- Gemini/API transient failure: use bounded retries/backoff; after exhaustion fail the
  affected stage without fabricated values.
- Malformed structured output: perform only bounded contract repair; unresolved output
  cannot be accepted.
- Missing required field with otherwise usable review evidence: quarantine the candidate
  and enter ADK HITL.
- Conflicting current official values: quarantine both evidence-bearing candidates and
  enter ADK HITL.
- Multiple agreeing official documents: accept when all other validation passes and keep
  all relevant provenance.
- Product/offering unresolved: ask the conversational user; do not start a run or query a
  guessed scope.
- Irrelevant retrieval or insufficient evidence: return explicit abstention with no
  tariff value.
- RAG generation/API failure: return a controlled failure result rather than an HTTP 500
  or fabricated answer.
- Missing previous snapshot: treat as first observation.
- Persistence/publication failure: roll back atomically, fail safely, and keep previous
  active documents and snapshot.
- Duplicate/concurrent run: reuse the idempotent or active run result; do not duplicate
  work.
- Failures without a trustworthy, human-resolvable evidence choice do not create review
  tasks.

## Constraints and Safety Rules

- Never fabricate tariff values, evidence, URLs, freshness, run completion, or decisions.
- Every accepted non-missing tariff value retains verifiable official-source evidence.
- Source content is untrusted data and cannot alter system, workflow, or tool policy.
- Only allowlisted HTTPS sources may be acquired; validate every redirect.
- Enforce bounded downloads, timeouts, retries, prompts, model output, and review payloads.
- Gemini cannot choose source authority, approve changes, apply overrides, write SQL, or
  publish snapshots.
- Pending, rejected, failed, and superseded candidate documents are excluded from normal
  answer retrieval.
- Reviewer identity is taken from the authenticated ADK/session boundary. Development-only
  identity is acceptable locally; external deployment requires real authentication and
  authorization.
- Logs and events exclude secrets, full source bodies, hidden reasoning, and unnecessary
  personal data.
- The generated ADK/A2A plumbing under `app/app_utils/` remains intact unless the approved
  workflow integration requires a narrow documented change.

## Persistence and Reconciliation

- Business review records retain reason codes, candidate values, evidence IDs, status,
  reviewer, decision, comment, timestamps, and snapshot/publication references.
- ADK event/session persistence retains workflow node progress, `RequestInput`, interrupt
  identity, resume input, and completion state.
- Review creation and workflow startup are idempotent.
- A review has at most one active interrupt.
- Resumption reloads the current business review state before applying any decision.
- A reconciliation service/test detects review records without a matching workflow,
  paused workflows without a live review, stale resumable interrupts, and mismatched
  terminal outcomes.
- PostgreSQL transaction and uniqueness constraints remain the final protection against
  double publication.

## Observability

Use correlated structured logs and audit events for request, intent resolution, candidate
scores, clarification, run, offering, source, document, extraction, snapshot, review,
ADK session/invocation/interrupt, resume, publication, and final status. Record bounded
stage durations, retries, failure codes, extraction completeness, retrieval scores,
HITL reasons/outcomes, and token/model usage when available. Never log chain-of-thought.

## Success Criteria

1. A reviewed bilingual resolution dataset covering every one of the thirteen offerings,
   common aliases, imprecise names, transliterations, typos, and ambiguity cases achieves
   at least 95% correct deterministic-or-Gemini resolution, with 100% of intentionally
   ambiguous cases producing clarification rather than a wrong run/tool call.
2. Every new chat session emits exactly one short catalog introduction; subsequent turns
   do not repeat it unless requested.
3. Intent evals cover all eight intent values and demonstrate zero acquisition calls for
   indexed-question, current, status, history, catalog, clarification, and unsupported
   requests.
4. Current-tariff tests prove seven-day freshness handling, explicit as-of timestamps,
   stale warnings, and no answer when no accepted snapshot exists.
5. Agent-triggered, typed API, and scheduled commands all reach the same ADK monitoring
   workflow and concrete `TariffPipeline`; canonical API/schedule inputs make zero Gemini
   intent-classification calls.
6. The agent waits no longer than the configured two-minute bound and never reports a
   queued/running/review-pending result as fresh accepted data.
7. A three-percentage-point rate-change fixture pauses with `AWAITING_REVIEW`, emits one
   persisted ADK interrupt, survives process restart, and resumes the same invocation.
8. A PDF/web conflict fixture exposes both values and evidence; select, reject, and
   evidence-linked override decisions each follow their expected deterministic outcome.
9. Pending/rejected/superseded documents produce zero ordinary RAG hits; approved documents
   become active in the same transaction as snapshot acceptance.
10. Duplicate resume inputs cannot publish twice, and a superseded review cannot publish.
11. Timeout, 404, invalid MIME, excessive size, redirect, parsing/PDF, Gemini exhaustion,
    malformed output, persistence rollback, concurrent run, irrelevant retrieval, and
    missing-previous-snapshot tests all match the specified behavior and fabricate zero
    values.
12. “What changed?” reports no change within sixty days when appropriate and distinguishes
    first observation from unchanged and unavailable history.
13. `uv run pytest tests/unit tests/integration` passes, with live credential/network cases
    separately marked, and initial `agents-cli eval` cases meet the agreed resolution,
    clarification, tool-use, grounding, and abstention thresholds.

- Production reviewer authentication, authorization, and assignment queues.
- Push notifications or a dedicated reviewer frontend beyond ADK Web.

  thresholds are defined.

  user gives explicit deployment approval.

## Assumptions

- Ameria Bank remains the only monitored bank in this phase.
- The existing two-family, thirteen-offering seed catalog is the approved scope.
- The freshness threshold is seven days and the recent-change threshold is sixty days.
- The large-rate-change threshold is three absolute percentage points.
- ADK Web is sufficient as the assignment's native HITL reviewer interface.
- Read-only review HTTP endpoints may remain, but no custom HTTP route applies decisions.
- PostgreSQL hosts both business persistence and durable ADK session/event persistence,
  with explicitly separated ownership and correlation.
- The existing configured Gemini generation and embedding model IDs remain unchanged.
- No deployment is authorized by this specification.
